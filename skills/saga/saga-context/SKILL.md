# /saga-context

Maintain `.planning/CONTEXT.md` — the project's living glossary and "why it's shaped this way" doc. The single
source of truth for domain terms, so code comments and other docs **link** to it instead of re-explaining.
Distinct from `.planning/intel/` (the RAG-fed JSON layer, regenerated by tooling — do not hand-edit that here).

## Process

1. If `.planning/CONTEXT.md` is absent, create it with a `# Context: <project>` heading and a `## Glossary` section.
2. Add or refine the entry for the term/concept: a tight definition in operator terms (1–3 sentences), and where
   useful, why it's that way (the constraint or trade-off behind it). Reach for leading words rather than long prose.
3. **Single source of truth:** if the term is already defined, refine the existing entry — do not create a second.
   If it's defined elsewhere (a code comment, another doc), replace that with a pointer to CONTEXT.md.

## Completion criterion

DONE when CONTEXT.md exists, the term has **exactly one** entry (no duplicate), the definition is concrete enough
that a new operator could use it, and any pre-existing restatement elsewhere now links here instead. Keep entries
short — CONTEXT.md is a glossary, not a design doc (that's `docs/` or a decision record).
